# /srabotka: исправление события успеха формы

Состояние на **9 октября 2026 года**: живая тестовая отправка формы `pz-lead-srabotka` получила подтверждение успеха на странице. **Получение живого Lead в Meta подтверждено в обычном обзоре Events Manager** после двух контрольных отправок с исправлением: Lead («Лид») — «Активно», источник «Браузер», 2 события; последние данные — 14 минут назад. В подробностях стандартного события Lead подтверждено всего 2 браузерных события. В том же обзоре отображалось 16 PageView. Подтверждения отдельного потока Meta Test Events и живой сверки UUID запроса с `pz_form_success` в этой проверке нет. Исправление опубликовано в Tilda на странице `276459603`, блок `4362348003`; публикация подтверждена интерфейсом. После перезагрузки обычной `/srabotka` проверены `tildaform:aftersuccess`, общий `event_id` в FormData, отсутствие плейсхолдеров и сохранение действующего адреса приёмщика.

## Исправление

В сохранённом опубликованном обработчике новый UUID попадал только в FormData, отдельно от скрытого `event_id`. После успешного ответа обработчик показывал успех и очищал форму, но не отправлял `tildaform:aftersuccess`.

[Исправленный обработчик](emergency-handler.fixed.js) сохраняет или создаёт одно скрытое поле `event_id`, передаёт тот же ID в FormData и один раз отправляет всплывающее `tildaform:aftersuccess` после успешного ответа, до reset. Действующий общий модуль аналитики 2.1 создаёт `pz_form_success` и очищает ID; новый обработчик не добавляет второй `dataLayer.push`. При ошибке успех не создаётся, ID и данные остаются для повторной попытки. Повторная отправка во время запроса блокируется.

## Воспроизводимые автономные проверки

[Тесты](emergency-handler.test.mjs) исполняют [сохранённый исходный обработчик](published-emergency-handler.js), исправление и [неизменённые функции и listener успеха общего модуля аналитики 2.1](analytics-success-listener-v2.1.fixture.js) с имитацией DOM и ответа запроса. Фрагмент аналитики является тестовой зависимостью, его нельзя отдельно устанавливать на страницу.

Проверено **8 из 8** сценариев:

1. Исходный обработчик воспроизводит разные ID и отсутствие канонического успеха.
2. Успешный ответ использует общий ID и создаёт один успех до reset.
3. Отсутствующее скрытое поле создаётся и получает тот же ID.
4. Ошибка HTTP не создаёт успех; повтор использует сохранённый ID.
5. Сетевая ошибка сохраняет данные и ID без успеха и reset.
6. Повтор submit во время запроса не создаёт второй запрос.
7. Повторная загрузка обработчика не добавляет вторую привязку.
8. Следующая независимая заявка получает новый ID.

Запуск из этой папки:

```sh
node --test emergency-handler.test.mjs
```

Тесты не используют сеть, CRM или Meta и не подтверждают доставку живого Lead.

## Публикация и живая приёмка

В публичных исходниках URL приёмщика и контакт поддержки заменены `__KEEP_EXISTING_WEBHOOK_URL__` и `__KEEP_EXISTING_SUPPORT_PHONE__`. При публикации нужно сохранить действующий URL и действующее сообщение ошибки из блока Tilda. Плейсхолдеры не являются рабочими настройками.

Заменяется именно существующий обработчик формы `pz-lead-srabotka` на странице `/srabotka`; вторая копия обработчика или аналитики не добавляется. Сохранение исходников в GitHub не публикует изменение в Tilda.

Получение Lead подтверждено отдельно от автономных тестов. Для полной проверки контракта формы остаётся зафиксировать один UUID в запросе и `pz_form_success` и отсутствие успеха при ошибке. Техническая подготовка Meta завершена: аудитория **«POZHARNIK — заявки Lead 180 дней»**, ID `120248972004510780`, создана 09.10.2026 в 12:15; сохранённый редактор подтвердил источник POZHARNIK — pozharnik.kz, событие Lead и удержание 180 дней. Аудитории посетителей 30/90 — отдельные списки без внутреннего исключения Lead. В будущей группе объявлений Lead 180 нужно исключить явно. Правила, статусы и подтверждение выключенных кампаний зафиксированы в [общем стандарте](../../META_PIXEL_STANDARD_2026-10-09.md).
